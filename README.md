# FursuitWeather for Windows

[![CI](https://github.com/223n/FursuitWeather_Windows/actions/workflows/ci.yml/badge.svg)](https://github.com/223n/FursuitWeather_Windows/actions/workflows/ci.yml)

着ぐるみ天気予報[FursuitWeather](https://fursuit-weather.223n.tech/)のWindows向けクライアントです。
デスクトップに常駐し、着ぐるみで活動してよい状況かを目の端で確かめられるようにします。

2026年9月16日に、プレリリースでない最初の版`v0.3.0`を公開しました。
入手は[Releases](https://github.com/223n/FursuitWeather_Windows/releases/latest)からです。

## できること

表示する面は3つです。

- 最前面に置く小さなカード（小窓）
- タスクトレイへの常駐と、判定が悪くなったときのトースト通知、毎朝のブリーフィング
- 会場の専用の端末で使う、全画面の掲示モード（`v0.3.0`で追加）

### 小窓

地点と時刻、判定のバッジ、連続して着ていられる時間、補足の数値、データの出典を1枚のカードに出します。
判定は色だけでなく、記号と文字でも示します。

- カードの大きさは300×200で固定です
- 既定では最前面に置き、フォーカスを奪いません。全画面のアプリやプレゼンテーションのあいだは自動で隠れます
- 設定で「常に手前」「ほかの窓に隠れてよい」「トレイだけ」から選べます
- カードは掴んで動かせます。カードの周りの余白は、クリックを背後の窓へ通します
- クリックスルーを入れると、カードも含めてすべてのクリックを背後へ通します。`Ctrl+Alt+F`かトレイのメニューで切り替えます
- クリックスルーは30秒で自動的に戻ります。戻したくないときは、トレイの「自動で戻さず保つ」を選びます

小窓はタスクバーとAlt+Tabのどちらにも出ません。
見失ったときは、トレイのメニューの「小窓の位置を戻す」で既定の位置（主モニターの右上）へ戻せます。

### トレイと通知

タスクトレイに常駐し、予報を11分ごとに取り直します。
判定が悪くなったときは、トーストで知らせます。

比べるのは連続して着ていられる時間（`activityMinutes`）で、判定の段階（`grade`）ではありません。
段階の数字は低温側で`grade 3`を飛ばし、上がっても着ていられる時間は変わらない場合もあるためです。
見るのはいまの時間だけではなく、この先3時間で最も厳しい時間です。

| 通知 | 出すとき | 抑え方 |
| ---- | ---- | ---- |
| 着用中止 | 連続して着ていられる時間が0分になった | 1日1回 |
| 短縮 | 連続して着ていられる時間が前回より短くなった | 同じ種類は2時間あける。1日6件まで |
| 熱中症警戒アラート | 環境省の発表が出た。警戒から特別警戒へ上がった | 抑えない |
| 再開 | 0分から着られる状態へ戻った | 1日1回 |

改善は、着用中止からの再開を除いて知らせません。
「もう安全だ」と誤って読ませないためです。

毎朝8時には、判定が変わっていなくても朝のブリーフィングを1件出します。
今日の最も厳しい判定、活動に適した時間帯、冷房の要否、急な暑さ、公式の発表の状況をまとめます。
判定が最上段に張り付いて変わらない日にも、黙り込まないためです。
正午を過ぎたら、その日のぶんは出しません。

深夜でも通知を止めません。
熱中症警戒アラートは午前5時にも発表されるためです。
静かにしたい時間帯は、Windowsの「応答不可」に任せます。
着用中止と熱中症警戒アラートだけは、緊急の通知（`AppNotificationScenario.Urgent`）として出します。

トースト通知は設定で切れます。
トーストを出せない環境では、小窓とトレイのバルーンで代わりに知らせます。

Windows 11は、トレイのアイコンを既定でタスクバーの「^」の中へ隠します。
常に見えるようにするには、タスクバーの設定で表示を切り替えてください。

### 掲示モード

会場の専用の端末に置き、来場者へ判定を掲げ続けるための全画面のスライドです。
`v0.3.0`で加わりました。
表示の細部は、本体のWebの掲示の画面（`/display`）に揃えています。

スライドは「いまの判定」「この後の予報」「3日間の天気」「全国の天気」の順に巡ります。
暑さで判定の段階が3以上のときだけ、「もしものとき」の手順を加えます。
上の帯には地点名、いまの判定、この先3時間の悪化、環境省の発表、注意を出します。
下の帯には「HH:MM時点」とデータの出典を出します。

- 始めるのはトレイの「掲示を始める」からです。設定の「起動したら掲示で始める」と自動起動を組み合わせると、停電や再起動のあとも掲示へ戻ります
- 終えるには、Escキー、画面の「掲示を終える」、トレイのメニュー、`Ctrl+Alt+D`のどれかを使います
- 掲示を出すモニターは設定で選べます。そのモニターが外れたときは、残ったモニターへ移して注意を出します
- 地点は小窓と共通です。設定の検索の欄で、地名か郵便番号から選べます。既定の地点のままなら、掲示に注意を出します

掲示のあいだは、次のように振る舞います。

- トーストをすべて出しません。着用中止と熱中症警戒アラートも出しません。掲示そのものが伝え、トーストは来場者の見る画面に重なるためです
- 自動の更新のインストールを保留し、掲示を終えたときに入れます
- 画面と端末のスリープを抑えます。スクリーンセーバーは止められないため、設置のときに切ってください

Webの掲示の画面にある「推定の警戒帯」（暑さ指数33以上で出す帯）は出しません。
出すには、クライアントが閾値で判定することになるためです。
**そのため同じ会場のWebの画面と比べ、安全側の情報が1つ少なくなります。**

## 判定はAPIに任せます

判定そのもの（暑さ指数の計算、レベルの判定、連続活動時間の算出）は本体のAPIが行います。
このクライアントは受け取ったJSONを描くだけで、判定のロジックを複製しません。
判定の仕組みは本体の[判定ロジック](https://github.com/223n/FursuitWeather/blob/main/docs/logic.md)にあります。

クライアントが自分で決めるのは、次の4つだけです。

1. いまの時間にあたる行を選ぶ
1. `generatedAt`を基準に、データが古くなっていないかを見る
1. 取り直しの間隔と再試行を制御する
1. `grade`とレベルの名前から、配色と記号を引く

判定のラベルは、APIが返した文字をそのまま出します。
通知をいつ出すかの規則はクライアントが持ちますが、比べる値はAPIが返したものです。
詳しくは[APIの利用](docs/api-client.md)と[通知の設計](docs/notifications.md)にあります。

## 送る情報

- 予報を取るときに送るのは、小数2桁（およそ1km四方）へ丸めた緯度と経度です
- 設定で地点を検索したときは、入れた地名か郵便番号を送ります
- 利用状況を集める仕組み（テレメトリ）は持ちません

## 動く環境

- Windows 11 22H2（ビルド22621）以降
- x64（配っているのはx64版だけです）
- インターネットへの接続

## インストール

1. [Releases](https://github.com/223n/FursuitWeather_Windows/releases/latest)から`FursuitWeather-X.Y.Z-x64-setup.exe`を取ります
1. 取ったファイルを実行します。管理者の権限は要りません
1. `%LOCALAPPDATA%\Programs\FursuitWeather`へ、使っている利用者のぶんだけ入ります

インストーラーは170MBほどあります。
トースト通知に使うWindows App SDKのランタイムと、`.NET`のランタイムを同梱しているためです。
`.NET`をあらかじめ入れておく必要はありません。
同じPCのほかの利用者が使うときは、その利用者でも入れてください。

### 未署名のため、SmartScreenの警告が出ます

インストーラーとアプリには、コード署名をしていません。
そのため、ダウンロードや実行のときにSmartScreenの警告が出ます。
「WindowsによってPCが保護されました」と出たら、「詳細情報」を押すと「実行」のボタンが出ます。
Smart App Controlを有効にしている端末では、起動そのものを止められることがあります。

実行する前に、取ったファイルがReleaseに載せたものと同じかを確かめられます。
同じReleaseに添えてある`update.json`の`sha256`と、手元のファイルのハッシュを比べてください。
PowerShellは大文字で出すため、大文字と小文字の違いは無視して比べます。

```powershell
(Get-FileHash .\FursuitWeather-0.3.0-x64-setup.exe -Algorithm SHA256).Hash
```

署名は、SignPath Foundationを第一の候補にしています。
申請の条件に「すでにリリース済みであること」が含まれるため、未署名で出したあとに申請し、通ったらリリースの手順へ組み込む予定です。
経緯は[開発環境とCI](docs/development.md)の「署名と配布」にあります。

### アンインストール

Windowsの「設定」の「アプリ」から消せます。
自動起動の登録、通知の登録、ショートカットも一緒に消えます。
設定と状態のファイル（`%LOCALAPPDATA%\FursuitWeather`）は残ります。
Windows App SDKのランタイムは、ほかのアプリが使っている可能性があるため残します。

## 自動更新

新しい版があるかの確認は、どの設定でも自動で行います。
起動の3分から10分後に1回、以後はおよそ24時間ごとです。
トレイの「更新を確認」や、設定画面の「今すぐ確認」からも確かめられます。

取り込み方は、設定画面で3つから選べます。

| 設定 | 取得 | インストール |
| ---- | ---- | ---- |
| 自動で更新する（既定） | 自動 | 自動 |
| 取得だけ自動で行う | 自動 | トレイの「更新をインストール」か、設定画面で押したとき |
| 何もしない（お知らせのみ） | 押したとき | 押したとき |

**既定は「自動で更新する」です。**
`0.3.0`までは「取得だけ自動で行う」が既定でした。
設定画面で取り込み方を変えたことがなければ、この変更を含む版から「自動で更新する」に変わります。
自分で選んだ設定は上書きしません。

未署名のため、インストーラーが確認の画面で止められると、アプリは起動し直さないまま止まるおそれがあります。
席を外すことの多い端末で心配なら、「取得だけ自動で行う」を選んでください。

「自動で更新する」のときも、次のあいだはインストールを先送りします。

- 全画面の表示中、応答不可の時間帯
- 起動してから10分のあいだ
- 掲示モードのあいだ
- 設定画面を開いているあいだ

インストールのあいだはアプリが20秒ほど止まり、自動で起動し直します。
従量制課金の接続とバッテリーでの動作中は、自動の取得を控えます。
控えるかどうかは設定で切り替えられます。

更新の中身は、次の順で確かめてから使います。

1. GitHub Releasesから`update.json`と署名の`update.json.sig`を取ります
1. アプリに埋め込んだ公開鍵（ECDSA P-256）で署名を確かめます。通らなければ使いません
1. インストーラーを`github.com`からだけ取り、大きさとSHA-256を照らします

仕組みの全体は[更新の仕組み](docs/update.md)にあります。

## 現在の状態

小窓、トレイ、トースト通知、朝のブリーフィング、自動更新、掲示モードが動きます。
ただし設計の文書に書いたもののうち、次はまだ作っていません。

- **小窓の折りたたみ**。設計では、折りたたんだバー（およそ220×44）を既定にし、ホバーかクリックで広げます。いまは300×200のカードで固定です
- **トーストのボタン**。設計では「もしものとき」「時間別を見る」「環境省の発表を見る」「2時間おやすみ」を置きます。いまは本文を押すと小窓が前に出るだけです
- 先読みの幅（既定3時間）と、朝のブリーフィングの時刻（8時）を変える設定
- 通知の履歴を見る手段
- コード署名
- 掲示モードの縦置きのモニターへの対応と、無人の端末で異常終了したときの扱い（いまはクラッシュの画面がOKを待って止まります）

### 確かめていないこと

**掲示モードは、実機の画面での確認が残っています。**
画面の外に描いた画像を使い、5枚のスライド、帯、注意の積み上げ、Escで終えられること、スリープの抑止の要求は確かめました。
次はまだ確かめていません。

- 全画面の窓がタスクバーを覆うか。ダイアログやトレイのメニューとどう重なるか
- 掲示先のモニターを見分ける値が、再起動や抜き差しのあとも変わらないか
- モニターを抜いたときに、窓がどこへ移るか
- モニターごとに倍率が違う構成で、窓がモニターいっぱいに収まるか
- スリープの抑止が効くか。抑えているあいだに画面のロックが働くか
- 拡大した文字が、遠くから読めるか
- 自前の全画面の窓に対して、Windowsが「割り込まない状態」をどう判定するか（`SHQueryUserNotificationState`）

掲示モードの外にも、確かめていない前提があります。

- 着用中止と熱中症警戒アラートの通知が、Windowsの「応答不可」を実際に突破するか
- 最前面の小窓が、配信や画面の共有に映り込むか
- 複数のモニターや、モニターごとに違う倍率での小窓の振る舞い

一覧は[未決事項とリスク](docs/open-questions.md)と、[掲示モード](docs/display.md)の「確かめていないこと」にあります。

## 開発

`C#`（`.NET 10`）とWPFで書いています。
決めた理由と、採らなかった案は[技術選定](docs/stack.md)にあります。

### 必要なもの

- `.NET` SDK 10（`winget install -e --id Microsoft.DotNet.SDK.10`）
- Visual Studio 2026、またはVS CodeとC# Dev Kit
- Node.js 22以上（日本語の文書の検査に使います）
- Inno Setup（インストーラーを作るときだけ）

### ビルドとテスト

```bash
dotnet build -warnaserror
dotnet test
dotnet format --verify-no-changes
```

表示と通知の規則は、UIに依存しない`FursuitWeather.Core`が持ちます。
そのためCIでは、LinuxとWindowsの両方のランナーでビルドとテストを回します。

配布用のインストーラーは次で作ります。

```powershell
./scripts/build-installer.ps1              # 配布用
./scripts/build-installer.ps1 -SkipRuntime # 組み立ての確認だけ。ランタイムを同梱しないため配れません
```

### リポジトリの初期設定

テンプレートから作った直後の設定を`scripts/setup.ps1`がまとめて行います。
PowerShell 7以上と、ログイン済みの`gh`（GitHub CLI）が要ります。

```powershell
./scripts/setup.ps1                    # 設定をまとめて行う
./scripts/setup.ps1 -RunsOn self-hosted # セルフホストのランナーも設定する
./scripts/setup.ps1 -DryRun            # 何をするかを表示するだけ
```

何度実行しても結果は同じで、失敗した項目は最後にまとめて表示します。
`Get-Help ./scripts/setup.ps1 -Full`で詳しい説明を読めます。

### 日本語の文書を検査する

Markdownの書式を`markdownlint`で、日本語の書き方を`textlint`で検査します。
規則は公開されている共有設定[@223n/lint-config-ja](https://www.npmjs.com/package/@223n/lint-config-ja)にあり、このリポジトリには「何を検査するか」だけを書いてあります。

```bash
npm install
npm run lint          # 書式と日本語をまとめて検査する
npm run lint:md:fix   # 書式の指摘を直す
npm run lint:ja:fix   # 日本語の指摘のうち、機械的に直せるものを直す
```

文体は「ですます調」です。
書き方の決まりは[CONTRIBUTING.md](CONTRIBUTING.md)にあります。

`main`と`develop`への`push`と、すべてのPull Requestで、CIが同じ検査をします。
CIではあわせて、`.NET`のビルドとテスト、ワークフローの構文（`actionlint`）、ワークフローの安全性（`zizmor`）を検査します。

## ブランチとリリース

GitFlowに沿って運用します。
ブランチの役割は[CONTRIBUTING.md](CONTRIBUTING.md)にあります。

```text
develop ──▶ release/vX.Y.Z ──(Pull Request)──▶ main ──▶ タグ vX.Y.Z と GitHub Release ──▶ develop へ戻す
```

### リリースする

1. Actionsの「リリース」を開き、「Run workflow」を選びます
1. `version`にリリースする版を入れます。`v`は付けません（例: `1.2.0`、`1.2.0-rc.1`）
1. ワークフローが`develop`から`release/vX.Y.Z`ブランチを切り、`package.json`の版を上げ、`main`へのPull Requestを開きます
1. Pull Requestの内容を確かめ、マージコミット（Create a merge commit）でマージします
1. 「リリースを公開する」ワークフローが動き、タグ`vX.Y.Z`を打ち、GitHub Releaseを下書きで作り、`main`を`develop`に戻します
1. 続けてインストーラーと更新のマニフェスト（`update.json`）を作り、Releaseへ添えます
1. マニフェストへの署名には、`release`環境での承認が要ります。承認すると署名を添え、下書きを外して公開します

版は`package.json`の`version`で管理します。
`develop`と`main`の版、最新のタグのどれよりも大きい版だけを受け付けます。
すでにあるタグや、開いたままの`release/*`ブランチがあると止まります。
`-rc.1`のようなプレリリースの版は、GitHub Releaseでもプレリリースになります。

`auto_merge`を有効にして実行すると、Pull Requestを人手で確かめずにマージし、公開まで一気に進めます。
ただし`main`に必須のチェックや承認のルールがあると、マージで止まります。
ワークフローが開いたPull RequestのCIは承認待ちのままで、ルールを満たせないためです。
その場合は人がPull Requestをマージすれば、公開のワークフローが続きを行います。

`develop`にPull Requestを必須にする規則がある場合、`main`から`develop`への戻しは毎回Pull Requestになります。
ブランチ名は`merge/vX.Y.Z-into-develop`です。
リリースのあとに、このPull Requestもマージコミットでマージしてください。

squashやrebaseでマージしないでください。
リリースノートに`develop`で取り込んだPull Requestが載らず、次の版のPull Requestが衝突します。

GitHub Releaseの本文は、マージしたPull Requestのタイトルとラベルから自動で作られます。
分類は`.github/release.yml`にあります。

### 緊急の修正（hotfix）

リリース済みの内容を急いで直すときは、`main`から`hotfix/名前`ブランチを切ります。
そのブランチで修正し、`package.json`の版も上げます。

```bash
npm version patch --no-git-tag-version
```

`main`へのPull Requestをマージコミットでマージすると、「リリースを公開する」ワークフローが`release/*`と同じように動きます。
版を上げ忘れると、同じ版のタグがすでにあるため止まります。
