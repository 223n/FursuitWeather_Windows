# 技術選定

開発言語とフレームワークを決めた記録です。
2026年9月9日の調査に基づきます。

## 結論

**C#（.NET 10）とWPFを採ります。**

対抗馬はTauri v2（TypeScriptとRust）でした。
比較の結果、Tauriが上回るのは初回インストーラーの大きさだけで、要件の中核で構造的に劣ると分かりました。

## 決め手

### 余白だけクリックを通す挙動が、WPFでは無償で手に入る

壁紙の上に置く小窓では、カードの部分は掴めて、余白は背後のデスクトップに抜けてほしくなります。
WPFの`AllowsTransparency=True`はレイヤードウィンドウの経路になります。
このときOSがピクセルの実効alphaでヒットテストを行うため、alphaが0の余白は自動で下へ抜けます。

Tauri v2の`setIgnoreCursorEvents`はウィンドウ単位の全か無かで、領域ごとの指定ができません。
Electronにある`forward`相当のオプションは、feature request #6164が2023年から未着手です。
しかも無視している間はウィンドウ自身が`mouseenter`と`mouseleave`を受け取りません。
そのため、JavaScript側でホバーを見て切り替えるという定番の回避策も成立しません。
Rust側でカーソル座標を毎秒60回ポーリングする仕組みを自作することになります。

### 通知の質に構造的な差がある

未パッケージの`.NET`アプリでも、`AppNotificationManager.Default.Register()`がCOMサーバーの登録を自動で行います。
シェルからの表示名とアイコンの取得も自動です。
AppUserModelIDの設定も、スタートメニューのショートカットも要りません。
ボタン付きの通知と、アプリ終了後のコールドローンチが公式にサポートされます。

Tauriのnotificationプラグインは、`desktop.rs`にボタンとアクションと活性化コールバックの実装がありません。
公式もActionsはモバイル限定と明記しています。
さらにAppUserModelIDをNSISインストーラーが作る`.lnk`に依存します。
その結果、インストール済みの環境でしか正しく動かず、開発中はPowerShellの名前とアイコンで表示されます。
「判定が厳重警戒に上がりました」という通知が、押しても何も起きないバナーになります。

### 既存のHTML資産を流用できるという前提が、実測で崩れた

Tauriを選ぶ最大の動機は、本体の`display.html`（会場表示モード）を持ち込めることでした。
実際に測ったところ、次のようになりました。

| ファイル | 再利用できる分 | 理由 |
| ---- | ---- | ---- |
| `display.html` 167行 | 14行（約8%） | 使えるのはFont AwesomeのSVGスプライトだけ |
| `display.css` 1028行 | ほぼ無し | `font-size`が例外なく`clamp()`の`vmin`基準で、300×200では全て下限に張り付く |
| `display.js` 1701行 | 200行から260行（12%から15%） | 捨てるのはスライド巡回、設定パネル、焼き付き対策など約1450行 |

`display.css`のうち155行は`@media (orientation: portrait)`の中にあり、横長の小窓では一度も発火しません。
グリッドも`repeat(6, 1fr)`のように大画面を前提としています。

本当に価値があるのはコードではなく、契約と規約でした。

- `docs/openapi.yaml`（OpenAPI 3.1.0、15のスキーマ定義）と`src/types.ts`があるため、DTOの定義はほぼ費用ゼロです
- `style.css`が持つ配色トークンと、バッジの規約（色・記号・文字の3要素）の約220行は、XAMLのResourceDictionaryへ機械的に写せます

この2つはどちらの技術を選んでも同じだけ活きるため、比較の優位を生みません。

## 要件別の適合

| 要件 | WPF | Tauri v2 | 根拠 |
| ---- | :--: | :--: | ---- |
| 透過の小窓 | ○ | ○ | どちらも設定で作れる。Tauriは`shadow: true`だと枠なし窓に1pxの白枠が付く |
| 部分クリックスルー | ◎ | × | WPFはOSのヒットテスト任せ。Tauriはウィンドウ単位のみで回避策も不成立 |
| 最背面への固定 | △ | △ | WPFは`SetWindowPos`と`WM_WINDOWPOSCHANGING`の実装が要る。Tauriの`alwaysOnBottom`は「試みるだけ」と明記 |
| マルチモニターとDPI | △ | △ | WPFは`Window.Left`と`Window.Top`がPer-Monitor V2で壊れており（dotnet/wpf#4127、修正予定なし）、物理ピクセル管理へ切り替える必要がある |
| トレイ常駐 | ○ | ○ | 実装の難度は同等 |
| トースト通知 | ◎ | × | 上記のとおり |
| 常駐時の占有 | ○ | △ | WPFは1プロセス。TauriはWebView2が6プロセス固定 |
| 配布 | △ | ○ | Tauriが上回る唯一の項目。WPFはトリミングとNative AOTが構造的に使えない |
| 既存リポジトリとの噛み合わせ | ○ | △ | TauriのMSIバンドラーが`1.2.0-rc.1`形式を拒否し、`release.yml`のプレリリース運用と衝突する |

署名とSmartScreenの扱い、`winget`への掲載条件は両者まったく同条件のため、比較の軸から外しました。

## 払う代償

この選択で失うものを明示します。

**WPFの`AllowsTransparency=True`は、子HWNDを一切描画しません。**
WebView2を含め、透過したウィンドウにHTMLを載せる道は完全に閉じます。
UIはXAMLとC#で新しく書きます。
本業のTypeScriptとHTMLとCSSは、この小窓では使えません。

あわせて次の2つも受け入れます。

- ClearTypeが無効になり、文字はグレースケールのアンチエイリアスになります
- MicaとAcrylicは`AllowsTransparency`と排他のため使えません

この3つを飲めるかが、選択の実体です。

## Tauriを選ぶべき場合

次の2つが同時に成り立つなら、Tauri v2が妥当になります。

- 小窓が「掴んで動かせるただの半透明の窓」でよく、余白のクリックを背後へ通す必要が無い
- 通知が「押しても何も起きないバナー」で足りる

この場合はTypeScriptとHTMLとCSSでUIを書けます。
インストーラーも数MBで済み、版の同期は`tauri.conf.json`の1行で片づきます。
その際は`bundle.targets`を`["nsis"]`に固定し、MSIのプレリリース制約を避けてください。
ポーリングは必ずRust側に置きます。
JavaScript側に置くと、ウィンドウを隠して5分後からChromiumの節電制限で毎分1回しかタイマーが回りません。
開発中は気付かず、本番で「通知が来ない」形で現れます。

逆に言えば、クリックスルーか通知のどちらか一方でも要件に残るなら、Tauriを選ぶ理由はありません。

## ウィジェットボードを外した経緯

当初はWindows 11のウィジェットボードへの対応も必須としていました。
この面だけが実装言語をOSの側で縛るため、いったんはC#が唯一の選択肢になりました。
ウィジェットプロバイダーはアウトプロセスのCOMサーバーとして実装し、MSIXでの配布が必須で、公式サンプルはC#とC++/WinRTしかありません。

そのうえで次のリスクが分かり、要件から外しました。

- MSIXをサイドロードした端末でウィジェットがボードに出ないという報告が、WindowsAppSDKのissue #4041（2023年12月起票）で未解決のままです
- 日本在住の個人はAzure Artifact Signingを使えず、署名の調達に別途の手当てが要ります
- Microsoftは2026年5月1日の公式ブログで、ウィジェットを「既定でより静かに」する縮小方向を表明しています

廃止や非推奨を示す一次情報は見つかりませんでした。
方向性の話であり、断定ではありません。

これを外したことで、MSIXとAdaptive Cardsが不要になり、署名も必須ではなくなりました。

当初はここに「トースト通知は未パッケージのままでも出せるため、単一の実行ファイルでの配布が視野に入る」と書いていました。
これは誤りでした。
`AppNotificationManager`はFrameworkパッケージの外にあるSingletonパッケージへ依存します。
そのため、Windows App SDKのランタイムの配置がどのみち要ります。
下の「配布方式」を見てください。

なお参考として、Microsoft Storeの個人開発者の登録料は2025年9月10日に撤廃されて無料になっています。
外した理由のうち署名費用の部分は、実は消えていました。

## 配布方式

インストーラーで配ります。
3点の組み合わせで決めました。

| 対象 | 決めたこと | 理由 |
| ---- | ---- | ---- |
| インストーラー | Inno Setup 6。ユーザー単位で非昇格 | `PrivilegesRequired=lowest`でUACを出さずに済みます。`AppVersion`が自由書式のため`1.2.0-rc.1`をそのまま通せます。`windows-2025`のランナーに同梱済みです |
| Windows App SDK | framework-dependent。`WindowsAppRuntimeInstall.exe`を連鎖インストール | self-containedにしてもSingletonパッケージが付いてこないため、通知が成立しません。framework-dependentならセキュリティ修正がFrameworkパッケージ経由で届きます |
| `.NET 10` | self-contained | `.NET Desktop Runtime`はシステム全体へのインストールしかなく、連鎖させると昇格が必須になります。非昇格を保つ唯一の手段です |

Windows App SDKと`.NET`で方針が逆になるのが要点です。
前者はself-containedにしても目的を果たさず、後者はself-containedにすると昇格の要求そのものが消えます。

Microsoft Learnは未パッケージのアプリ向けに、自前のセットアップからWindows App SDKのセットアップを連鎖させる手順を文書化しています。
公式に想定された運用です。

### 採らなかった配布の手段

| 候補 | 採らなかった理由 |
| ---- | ---- |
| MSIXと`.appinstaller` | 更新機構としては最も優れており、OSが8時間ごとに無音で更新します。ただし端末が信頼する証明書での署名が必須です |
| Velopack | 常駐アプリとの相性は最良ですが、`--framework`の対応一覧にWindows App SDKがありません |
| ClickOnce | `.NET 5`以降で`UpdateMode`の`Background`と`UpdateInterval`が非サポートです。常駐し続けるアプリには更新が届きません |
| Squirrel.Windows | 最終リリースが2020年9月で、実質止まっています |
| MSI（WiX） | `ProductVersion`がプレリリースの識別子を表現できません。上でTauriを落としたのと同じ壁です |

### 配布サイズ

**実測しました**（2026年9月9日、`0.3.0-rc.1`、win-x64）。

| 対象 | 実測 | 当初の推定 |
| ---- | ---- | ---- |
| インストーラー | 164.5MB | 約190MB |
| `WindowsAppRuntimeInstall-x64.exe` | 102MB | 約111MiB |
| 発行結果（圧縮前） | 219MB | ー |
| インストール後の占有 | 未計測 | 約300MB |

推定より小さく収まりました。
インストール後の占有だけは、実際に入れて数えていないため推定のままです。

重すぎると判断した場合、圧縮の手が2つあります。

- インストール時にランタイムをダウンロードする方式。約80MBになりますが、オフラインでの導入ができなくなります
- NuGetから取り出したMSIXを`PackageManager`で直接入れる方式。約130MBになりますが、ヘルパーを自作する手間が増えます

初版は同梱の方式を採ります。
結果が決まりやすく、オフラインの環境でも通るためです。

### 自動更新

Velopackが使えないため、更新の仕組みは自前で作ります。

利用者が3つのモードから選べるようにします。
自動で更新する、取得だけ自動で行う、お知らせのみ、の3つです。
既定は「取得だけ自動」にします。

設計は[更新の仕組み](update.md)にまとめました。

将来Velopackへ移る条件は「アプリの初回の起動時に、自分でランタイムを導入する経路」を実証できたときです。
その時点で利用者単位の配置と差分の更新が手に入ります。

## 検討して採らなかったもの

| 候補 | 採らなかった理由 |
| ---- | ---- |
| WinUI 3 | 透過ウィンドウが公式サポートの外です。microsoft-ui-xamlのissue #1247は2019年からBacklogのままです |
| Electron | 公式に「透過ウィンドウはリサイズ不可、透過領域のクリックスルー不可」と明記されています。`alwaysOnBottom`相当のAPIもありません |
| Avalonia | Windowsでの透過は全て対応し、v12でWebViewがOSS化されました。ただしWebViewの実績と日本語の情報が薄く、今回は未検証のため見送りました |
| PWA | ウィジェットボードを狙う場合には有力でした。その要件が消えたため、常駐と通知を満たせないこちらは落ちました |
