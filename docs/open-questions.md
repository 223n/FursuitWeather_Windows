# 未決事項とリスク

まだ決まっていない仕様と、確かめていない技術的な前提をまとめます。
2026年9月9日時点の内容です。

## 先に決めること

技術選定より優先度が高い項目です。
決まらないと設計が固まりません。

### 1. 「壁紙の上」の解釈

小窓を置く高さを決めます。

デスクトップのアイコンの**背面**（本当の壁紙の層）を指す場合、`Progman`への文書化されていないメッセージ`0x052C`と`SetParent`を使う手法しかありません。
これは非公式の手法です。
Windows 11 24H2では`WorkerW`の破棄が繰り返し報告され、25H2でも同種の報告があります。
`SetParent`はDPI認識の強制的なリセットを引き起こす可能性もあります。

**この手法は勧めません。**

アイコンの手前に置く小窓でよければ、`HWND_BOTTOM`への固定で足ります。
この論点はそこで消えます。

なお、どちらを選んでもWPFという結論は変わりません。
Tauriでも同じ地雷を踏むためです。

### 2. 「判定の悪化」の定義

通知を出す条件を決めます。

- `grade`が1段階でも上がったら通知するのか、厳重警戒より上への遷移だけにするのか
- 深夜も鳴らすのか
- 同じ状態が続くときの再通知をどう抑えるのか

本体のWeb版に前例がないため、ゼロから決めます。

### 3. 配布の形

「実行ファイルをダウンロードして置くだけ」を望むかどうかを決めます。

望む場合、Windows App SDKのランタイムの連鎖インストールを前提とする`AppNotificationManager`は使えません。
`Shell_NotifyIcon`のバルーンへ割り切ることになります。
バルーンはボタンを置けず、本文も256文字までです。

**これはアーキテクチャを左右します。**
後から変えると通知まわりを書き直すことになるため、Step 3の前に決めてください。

## 確かめていない技術的な前提

| 項目 | 状態 |
| ---- | ---- |
| ClearTypeが無効になった後の可読性 | レイヤードウィンドウを使う限り原理的に避けられません。`RenderOptions.ClearTypeHint`は不透明な背景に直接描く場合しか安全に使えません。Step 1で実機の確認が必須です |
| `AllowsTransparency`の実際の描画コスト | Microsoftの定量的な情報は2006年から2008年のXPとVistaの世代で止まっており、現行の環境の公式な測定値は見つかりませんでした。面積が小さく更新も低頻度なら実害は小さいと**推定**していますが、実測ではありません |
| Windows App SDK 2.4.0の未パッケージWPFでの実績 | 2.x系は比較的新しく、1.8系は2026年9月9日で保守終了です。self-containedかつ未パッケージで`Register()`がCOMの例外になる不具合（issue #6071）はPR #6725で修正済みですが、framework-dependentでの実挙動は自分で確かめるべきです |
| NSwagがOpenAPI 3.1を読めるか | NSwagの公式READMEは2.0と3.0だけを掲げ、3.1に言及がありません。本体の`openapi.yaml`は3.1.0です。駄目ならKiotaか手書きへ切り替えます |
| Font AwesomeのSVGをWPFのGeometryへ移すときの塗りつぶし規則 | SVGの既定はnonzero、WPFのPath Markup Syntaxの既定はEvenOddです。`fa-ban`などはデータの先頭に`F1`が要ると**推定**していますが、実際に描いて比べていません |
| Modern Standby環境でのスリープ復帰 | `PowerModeChanged`が期待どおり発火するかを一次情報で確認できていません。単調時刻による経過の判定を基本の層に置けば、イベントが届かなくてもtickの周期で復帰できます |
| Windows 11がトレイアイコンを既定で隠すか | 技術メディアの記述はあるものの、Microsoftの一次情報での裏づけが取れていません。実機での確認が要ります |

## 運用上のリスク

- **署名**は技術選定では解けません。[開発環境とCI](development.md)の「署名と配布」を見てください
- **Open-Meteoの無料枠**は非商用の条件付きです。利用者が各自の任意の座標でポーリングすると、エッジのキャッシュのヒット率が下がり、上流の消費が増えます。利用者が増えた場合の見通しを別に立てる必要があります
- **Windows App SDK 2.x系の保守期限は2027年4月29日**です。2.4に上げても期限は延びません。1.x系のようにマイナー更新で期限が伸びる挙動とは違います。3.0への移行を年次の作業として計画に入れてください。新しいStableを月次で検知するだけのジョブをCIに1本置くと、駆け込みの移行を避けられます
- **`windows-latest`は予告なく更新されます**。2026年6月にWindows Server 2025とVisual Studio 2026へ移行済みです。再現性を重視するなら`windows-2025`のような明示のラベルに固定する選択肢があります

## 見積もりの不確実性

各Stepの日数と、移植の行数の見積もりは設計上の試算です。
実際に書いて計測したものではありません。
3割程度の振れは見込んでください。

[技術選定](stack.md)に載せたメモリーの数値は、1台での測定であり、他のアプリを代理の指標にしたものです。
FursuitWeatherのクライアント自体を測った値ではありません。
結論は「クリックスルー」「通知」「資産の流用」の3点で成り立っており、この3つは一次情報で確認済みです。
占有と配布の数値は補助的な根拠として扱ってください。
