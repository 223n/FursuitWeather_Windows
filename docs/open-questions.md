# 未決事項とリスク

まだ決まっていない仕様と、確かめていない技術的な前提をまとめます。
2026年9月9日時点の内容です。

## 先に決めること

技術選定より優先度が高い項目です。
決まらないと設計が固まりません。

### 1. 「壁紙の上」の解釈

小窓を置く高さを決めます。

デスクトップのアイコンの**背面**（本当の壁紙の層）を指す場合、`Progman`への文書化されていないメッセージ`0x052C`と`SetParent`を使う手法しかありません。
これは非公式の手法です。
Windows 11 24H2では`WorkerW`の破棄が繰り返し報告され、25H2でも同種の報告があります。
`SetParent`はDPI認識の強制的なリセットを引き起こす可能性もあります。

**この手法は勧めません。**

アイコンの手前に置く小窓でよければ、`HWND_BOTTOM`への固定で足ります。
この論点はそこで消えます。

なお、どちらを選んでもWPFという結論は変わりません。
Tauriでも同じ地雷を踏むためです。

### 2. 「判定の悪化」の定義

通知を出す条件を決めます。

- `grade`が1段階でも上がったら通知するのか、厳重警戒より上への遷移だけにするのか
- 深夜も鳴らすのか
- 同じ状態が続くときの再通知をどう抑えるのか

本体のWeb版に前例がないため、ゼロから決めます。

## 決まったこと

### 配布の形

インストーラーで配ります。
Inno Setup 6で利用者単位の非昇格インストーラーを作り、Windows App SDKのランタイムを連鎖インストールします。
これにより`AppNotificationManager`を使えます。
詳しくは[技術選定](stack.md)の「配布方式」にあります。

当初は「実行ファイルを置くだけ」と通知の質を天秤にかけていました。
しかし分岐点は配布の形ではなく、**Windows App SDKのランタイムを配るかどうか**でした。
self-containedにしても`AppNotificationManager`が依存するSingletonパッケージは付いてこないため、「置くだけ」で通知を成立させる道はもとからありません。

### 自動更新の扱い

利用者が3つのモードから選べるようにします。
自動で更新する、取得だけ自動で行う、お知らせのみ、の3つです。
既定は「取得だけ自動」です。

更新があるかの確認だけは、どのモードでも自動で行います。
設計は[更新の仕組み](update.md)にあります。

## 運用上のリスク

- **署名**は技術選定では解けません。[開発環境とCI](development.md)の「署名と配布」を見てください
- **Open-Meteoの無料枠**は非商用の条件付きです。利用者が各自の任意の座標でポーリングすると、エッジのキャッシュのヒット率が下がり、上流の消費が増えます。利用者が増えた場合の見通しを別に立てる必要があります
- **Windows App SDK 2.x系の保守期限は2027年4月29日**です。2.4に上げても期限は延びません。1.x系のようにマイナー更新で期限が伸びる挙動とは違います。3.0への移行を年次の作業として計画に入れてください。新しいStableを月次で検知するだけのジョブをCIに1本置くと、駆け込みの移行を避けられます
- **`windows-latest`は予告なく更新されます**。2026年6月にWindows Server 2025とVisual Studio 2026へ移行済みです。再現性を重視するなら`windows-2025`のような明示のラベルに固定する選択肢があります
- **`.NET`をself-containedにするため、公式に「Not serviceable」の扱いになります**。`.NET`の脆弱性の修正は、アプリを出し直さないと利用者へ届きません。月次程度のリリース運用が前提になります
- **利用者単位のインストールは、複数の利用者がいる端末で重複します**。ランタイムも実行した利用者にだけ登録されます。共用のPCを想定に入れるなら考え直しが要ります
- **Inno Setupの条文は無償で商用も認めています**。ただし2025年8月12日の6.5.0以降、開発元が年間収益で5000米ドルを超える商用の利用者へ有償ライセンスの購入を求めています。非営利なら対象外ですが、寄付の収入も収益に算入されます

## 見積もりの不確実性

各Stepの日数と、移植の行数の見積もりは設計上の試算です。
実際に書いて計測したものではありません。
3割程度の振れは見込んでください。

[技術選定](stack.md)に載せたメモリーの数値は、1台での測定であり、他のアプリを代理の指標にしたものです。
FursuitWeatherのクライアント自体を測った値ではありません。
結論は「クリックスルー」「通知」「資産の流用」の3点で成り立っており、この3つは一次情報で確認済みです。
占有と配布の数値は補助的な根拠として扱ってください。

## リポジトリの残作業

技術選定とは別に、テンプレートから作った直後の作業が残っています。

- `package.json`の`name`が`repo-template`のままです
- `package.json`の`description`と、ルートの`README.md`がテンプレートの内容のままです
- `scripts/setup.sh`をまだ実行していません
