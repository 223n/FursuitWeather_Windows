# APIの利用

本体のAPIを読むときに守ることをまとめます。
数値は本体のソースで確かめたものです。

APIそのものの仕様は本体の[API仕様](https://github.com/223n/FursuitWeather/blob/main/docs/api.md)にあります。
機械可読な定義は`docs/openapi.yaml`（OpenAPI 3.1.0）にあり、DTOの生成に使えます。

## 使うエンドポイント

| エンドポイント | 用途 |
| ---- | ---- |
| `GET /api/forecast` | 地点の予報。小窓の表示の中心になります |
| `GET /api/alert` | 環境省の熱中症警戒アラートの発表状況 |
| `GET /api/national` | 主要都市の当日の天気。掲示モードの全国の天気に使います。取れなかった都市は含まれません |
| `GET /api/geocode?q=` | 地名か郵便番号から座標を引きます。設定画面の地点の検索に使い、押したときだけ呼びます |

`GET /api/badge.svg`は主要12都市と登録済みのイベント開催地しか受け付けません。
自宅の座標の小窓には使えないため、当面は対象外とします。

認証はありません。
APIキーも要りません。

## ポーリングの間隔

本体の`public/display.js`の値をそのまま踏襲します。

| 対象 | 間隔 | 定数名 |
| ---- | ---- | ---- |
| 予報 | 11分 | `FORECAST_POLL_MS` |
| アラート | 31分 | `ALERT_POLL_MS` |
| 失敗時の再試行 | 60秒 | `RETRY_MS` |

正常なレスポンスには`Cache-Control: public, max-age=600`が付きます。
つまり10分はキャッシュが再利用されます。
これより短い間隔で叩いても新しいデータは返らず、上流の無料枠を削るだけです。

上流の気象データはOpen-Meteoです。
データそのものはCC BY 4.0ですが、無料APIの利用規約に非商用の制限があります。
`/api/forecast`の1件が上流の3本の呼び出しに広がるため、利用者が増えたときの見通しは別に立てる必要があります。

## タイムアウト

HTTPのタイムアウトは15秒から20秒にします。

Workerの側は上流に10秒待ち、5xxのときに1回だけ再試行します。
クライアント側を10秒で切ると、この正常な復旧の経路を潰してしまいます。

## 座標の丸め

**緯度と経度は小数2桁に丸めてから送ります。**
丸める処理はUIの層ではなく、HTTPクライアントの層に置いてください。

丸め方は本体の`src/logic/round.ts`の`round2`（`Math.round(value * 100) / 100`）に合わせます。
JavaScriptの`Math.round`はちょうど半分のときに正の無限大の側へ丸めるため、`.NET`の`MidpointRounding.AwayFromZero`とは負の値で結果が食い違います。
丸めた座標は上流のキャッシュのキーになるので、本体と同じ演算をなぞってください。

本体は座標を小数2桁（約1km四方）に丸めて扱うと公開しています。
Cloudflareのinvocation logはクエリ文字列を丸めずに記録するため、丸めずに送るとこの約束が破れます。

## 出典の表示

レスポンスの`attribution`を、常に見える位置に描きます。
文字列をハードコードせず、レスポンスから取った値を使ってください。

## JSONの読み方

寛容な側に倒します。

- 知らないフィールドは無視します
- nullを許すフィールドが多くあります。`days[].airQuality`は構造ごとnullになり、その中の`pm25Mean`なども個別にnullになります
- `weatherCode`が`-1`のときは欠測です
- `hours[]`は欠測の時間が配列から除かれるため、1時間ごとの連続を保証しません

### 時刻の扱い

`hours[].time`は`2026-08-15T09:00`のような、タイムゾーンを持たない日本時間の文字列です。

**`DateTimeOffset`で受けないでください。**
`DateTimeOffset`はオフセットが無いときに実行するマシンのローカルのオフセットを補います。
開発機は日本時間のため正しく動き、UTCのCIランナーでだけ9時間ずれます。
テストが通ってしまう種類の不具合です。

`DateTime`（`Kind`は`Unspecified`）で受け、使う直前に`TimeZoneInfo`で日本時間として明示的に解釈します。

### 配列の添字

`hours[i + 1]`を1時間後とみなすコードを書かないでください。
欠測のある日にだけ壊れ、平常時のテストでは再現しません。
`time`の値で突き合わせます。

## User-Agent

連絡先の分かるUser-Agentを名乗ります。
本体が上流に対して`FursuitWeather (https://github.com/223n/FursuitWeather)`と名乗っており、それに揃えます。

```text
FursuitWeather_Windows/1.0 (+https://github.com/223n/FursuitWeather_Windows)
```

## 判定ロジックを複製しない

暑さ指数の計算、レベルの判定、連続活動時間の算出は、すべてAPIの側で完結しています。
クライアントに残るのは次の4つだけです。

1. いまの時間帯にあたる行を選ぶ
1. `generatedAt`を基準に、表示中のデータが古くなっていないかを判定する
1. ポーリングの間隔と再試行を制御する
1. `grade`から配色と記号を引く

掲示モードは、1つ目を「この後の6時間」と「日付で日を選ぶ」まで広げて読みます。
どちらも時刻と日付の値で突き合わせるだけで、判定ではありません。
推定の警戒帯（暑さ指数33以上）と、洗濯のレベルから配色を引く表は、この範囲の外なので写しません。
照合の全体は[掲示モード](display.md)にあります。

判定を複製するのは、実測の暑さ指数を手で入力する機能を作る場合だけです。

## 既存資産のうち使えるもの

**訂正**: この節はかつて「判定の悪化を検知して通知する仕組みは、本体のWeb版にありません。前回の`grade`と比べる機構が無いためです」と書いていました。
誤りでした。
`public/app.js`の`renderForecastDiff`（1510行）が、まさに前回の`grade`と比べています。

そのまま写せるものが4つあります。

- 差分の検知（`before.grade !== after.grade`と`after.grade > before.grade`による悪化の判別）
- 通知の抑制（変更内容の署名を保存し、同じ内容の再表示を止める方式）
- 明示の操作のあとに基準を張り直し、偽の通知を防ぐ設計（`syncWatchBaseline`、1859行）
- 悪化の方向にだけ反応する非対称の制御（`applyTimerOutdoor`、3400行）

新しく実装するものが3つあります。

- ヒステリシス。リポジトリ全体に実装がありません
- 深夜の抑制。自前では持たず、Windowsの「応答不可」に委ねます
- OSの層の通知。Web版は`Notification` APIを使っておらず、通知はすべて前面に表示中の画面内のフィードバックです

Web版の見守りモードは「前面のときしか鳴らないから抑制が甘くても成立していた」設計です。
`app.js:1882`が`visibilityState`を見て、前面でなければ再取得ごと止めます。
常駐するアプリはこの前提を失うため、**抑制はWeb版より厳しくします。**

詳しくは[通知の設計](notifications.md)にあります。

配色は本体の`public/style.css`が持つ、色覚多様性へ配慮したトークンを写します。
バッジは色と記号と文字の3要素で表す規約になっており、これも踏襲します。
色だけで状態を伝える表示にしないでください。
