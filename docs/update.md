# 更新の仕組み

アプリを新しい版へ入れ替える仕組みをまとめます。
配布方式そのものは[技術選定](stack.md)の「配布方式」にあります。

## 実装の段階

一度には入れません。
安全の度合いが高い順に分けます。

| 段階 | 中身 | 状態 |
| ---- | ---- | ---- |
| 1 | 版の比較とマニフェストの検証 | **済み** |
| 2 | 署名鍵の用意と、CIでのマニフェストの生成 | **済み** |
| 3a | 抱え方、インストーラーの引数、`/WAITPID`の受け口 | **済み** |
| 3b-1 | 出来事を状態へ書き入れる規則（成否の確定、失敗の記録） | **済み** |
| 3b-2 | 実際の取得と、全体の繋ぎ込み | **済み** |
| 4a | 2つのゲート、保留の条件、再試行の抑制 | **済み** |
| 4b | 確認の周期と再提示の間隔 | **済み** |
| 5 | 設定画面 | 未着手 |

段階1をCoreへ置きました。
判断の中核がすべてここへ集まるためです。
署名、巻き戻しの検知、取得先の制限は、UIへ触れずに固められます。
Linuxのランナーでもテストが回ります。

### 承認が要るのは署名だけです

リリースの経路を3つのジョブに割りました。

| ジョブ | 承認 | やること |
| ---- | ---- | ---- |
| マニフェストを作る | 不要 | インストーラーの大きさとハッシュから`update.json`を組み立てます |
| **マニフェストへ署名する** | **要る** | `release`環境の私有鍵で署名します |
| Releaseへ添える | 不要 | `update.json`と`update.json.sig`を上げます |

**私有鍵に触るのは真ん中だけです。**
1つのジョブにまとめると、組み立てと添付まで承認待ちになり、リリースのたびに手が止まります。

署名したあと、同じジョブの中で公開鍵に戻して検証し直します。
通らないものは配りません。

### 組み立てた形を、その場で確かめます

`jq`でクライアントと同じ規則を当てます。
満たさないものへ署名しても、配った先で弾かれるだけです。

**弾かれた側からは「更新が来ない」としか見えません。**
静かに失敗する経路のため、出す前に止めます。

同じ形をテストの側にも置いてあります（`Fixtures/update-manifest.json`）。
組み立てる側と読む側は別々に書かれているため、片方だけを変えたときに気付ける場所が要ります。

### 署名の形式

- 曲線はECDSA P-256
- ハッシュはSHA-256
- 署名の形式は**DER**（`openssl dgst -sha256 -sign`が出すもの）
- 公開鍵はSPKIのPEMでアプリへ埋め込みます

形式が食い違うと、正しい署名でも通りません。
`openssl`で署名する前提のため、`.NET`の既定であるP1363（`r||s`）ではなくDERにそろえます。

### ゲートの置き方

段階4aで入れたものの要点です。

**判定するのは「自動で進めてよいか」だけです。**
利用者がボタンを押したときはゲートを通しません。
抑制は自動の側にだけ効かせ、手動の経路は常に生かします。

見送る条件はゲートごとに違います。

| ゲート | 見送る条件 |
| ---- | ---- |
| 取得 | 従量制課金、電池、再試行の待ち、自動の遮断 |
| 適用 | 割り込めない状態、起動から10分未満、前回の中断、再試行の待ち、自動の遮断 |

全画面や起動直後で**取得は妨げません。**
裏で受け取るだけで割り込まないためです。

**前回の中断はモードより先に見ます。**
押すのが利用者だとしても、壊れた状態への上書きは確認を挟ませます。

### 実機で端から端まで通しました

2026年9月11日、公開済みの`v0.3.0-rc.4`を相手に通しました。

| 段階 | 結果 |
| ---- | ---- |
| 確認 | 本物の`update.json`と署名を取り、アプリに埋め込んだ鍵で検証 |
| 判定 | rc.3を名乗る版でrc.4を「更新あり」と判定 |
| 取得 | 182,004,748バイトを18秒。大きさとSHA-256を掴んだハンドル越しに照合 |
| 引き渡し | 狙いを保存してからインストーラーを起動し、自分を終えた（10秒） |
| 待ち | インストーラーが呼び元のPIDの終了を待ってから入れ替えた |
| 再起動 | インストーラーがrc.4を起動し直した（全体で20秒） |
| 確定 | 次の起動で`Installing`から`Succeeded`へ確定 |

インストーラーへ渡った引数も記録で確かめています。

```text
/SP- /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /RESTARTEXITCODE=3010 /NOCANCEL
/LOG="...\logs\install-0.3.0-rc.4.log" /DIR="...\Programs\FursuitWeather" /WAITPID=24168 /RELAUNCH=1
```

### 同じ時刻のマニフェストを「古い」と扱っていました

段階1では、生成時刻が前回と**同じ**マニフェストも弾いていました（`<=`）。

新しい版が出るまで、確認のたびに同じマニフェストが返ります。
そのため取得に1度失敗すると、次の確認では同じものが「古い」とされ、**二度と取り直しませんでした。**

設計の「前回の成功時より古ければ無視」に合わせ、厳密に古いものだけを弾くよう直しました（`<`）。
署名は偽造できないため、同じものを出し直されても害はありません。

### 敵対的なレビューで7つの欠陥を直しました

実機で通したのは、うまくいく経路だけでした。
そこで失敗の経路を5つの観点で洗い、指摘ごとに反証を試みました。
47件のうち17件が反証を生き残り、重なりをまとめると次の7つでした。

| 欠陥 | 直し方 |
| ---- | ---- |
| インストーラーが途中で止まると、誰もアプリを起動し直さない | `DeinitializeSetup`で起動し直す |
| 取得の失敗が版をまたいで積もり、5回で自動の取得が永久に止まる | 新しい版を見つけたら張り直し、上限は24時間で数え直す |
| 更新のトーストがアプリの生涯で5回しか出ない | 1つの狙いにつき5回とし、狙いが変わったら戻す |
| 保留と中断が、次の確認（22時間から26時間後）まで解けない | 1分ごとに手元の状態と環境だけで見直す |
| 新しい版が出た直後に、古い取得物を新しい版の名前で入れる | 取得物に版とSHA-256を持たせ、狙いが変わったら手放す |
| 取得済みでも確認のたびに捨てて取り直し、従量制の回線でも黙って取る | 手元のものを使い回し、「更新を確認」では大きさと理由を見せて尋ねる |
| 書き込みの待ちの最中にタイムアウトすると、例外が捕まらずに落ちる | 捕まえる型を基底の`OperationCanceledException`へ広げる |

いずれも、失敗を黙らせる方向の欠陥でした。
直した筋書きはテストに残し、壊すと落ちることもわざと壊して確かめています。

直したあと、実機で次を確かめました。

| 筋書き | 結果 |
| ---- | ---- |
| 取得したあと、別のプロセスとして起動し直す | 取り直さずに1.7秒で`Downloaded`。同じファイルを使った |
| 置いてあるファイルの1バイトを書き換える | 大きさが同じでもハッシュで弾き、別の場所へ取り直した |
| いまの版が追いつく | 置き場を空にし、`Idle`へ戻った |
| 人が`/VERYSILENT`で入れる | 起動しなかった |
| 更新から入れて成功する | 1回だけ起動し直した |
| 入れ替えるファイルを掴んで中止させる | 巻き戻したあと、`DeinitializeSetup`が起動し直した |
| 呼び元が動いたまま中止させる | 30秒待ったうえで、起動を見送った |

### 直した差分にも、もう一度レビューをかけました

12件のうち11件が反証を生き残りました。
重いものは、今回の差分より前からあった穴でした。

| 穴 | 直し方 |
| ---- | ---- |

| 手放した旧版の取得物が、保留のあいだ残り続ける | 置き場で使えるものが見つからなければ、その場で片付ける |

実機では次を確かめました。

| 筋書き | 結果 |
| ---- | ---- |
| rc.3の上へ、rc.4を更新として入れる | ランタイムを入れ終えた33ミリ秒後に起動し直した。起動は1回 |
| 置いた順序 | `FursuitWeather.Widget.dll`が451個のうち、アプリのファイルの最後に来た |

| 2つ目を起動する | 0.2秒で終わり、プロセスは1つのまま |

### 3回目のレビューで、2回目の直しの詰めを直しました

5件のうち4件が生き残りました。

| 穴 | 直し方 |
| ---- | ---- |
| ランタイムの導入に失敗すると、抑止されない`MsgBox`が起動し直しを止める | 起動し直してから`MsgBox`を出す |

### 確かめるための引数

| 引数 | 用途 |
| ---- | ---- |
| `--update-manifest-url=` | 確認先を差し替えます。`latest`はrcを指さないため、rcを試すときに使います。署名の検証は変わらず効きます |
| `--self-test-update` | 確認を1回通し、結果を`update-selftest.txt`へ書きます |
| `--self-test-update-install` | 上に加えて、取得できたらインストールまで進みます。「更新をインストール」を押したのと同じ経路です |

開発用のビルドから起動しているときはインストールしません。
`/DIR`に今の場所を渡すため、ビルドの出力先へインストールしてしまうからです。
`unins000.exe`が隣にあるかで見分けます。

1つしか動かないため、試すときは常駐しているアプリを先に終えてください。
動いていると、試す側のプロセスは1つ目に小窓を出させてすぐ終わります。

### 抱え方で分かったこと

**書き込みの権限は途中で落とせません。**

設計は「検証から実行までハンドルを開いたままにする」としています。
書くときは書き込みで開く必要があります。
一方で起動のときは、読み取りを共有していなければなりません。
managedのAPIに権限を落とす手段が無いため、いったん閉じて開き直すほかありません。

そのため**閉じてから開き直すまでの一瞬だけ隙が残ります。**
ディレクトリの名前を毎回変えているのは、その隙を狙いにくくするためです。
設計が「目標は解決ではなく、隙を狭めること」と書いているとおりの状態です。

開き直したあとは、書き込みと削除のどちらも拒みます。
読み取りだけを許すのは、プロセスの起動が読み取りで開くためです。
塞ぐと起動できません。

### `/WAITPID`は実機で確かめました

インストーラーが呼び元の終了を待つことを、8秒で終わる相手を用意して確かめました。

```text
16:28:19.418   更新: PID 22700 の終了を待つ
16:28:28.182   更新: 呼び元が終わった
16:28:28.483   Starting the installation process.
```

待ちは30秒で打ち切ります。
呼び元が固まったときに、インストーラーまで固まらせないためです。

`/RELAUNCH=1`のときだけ起動し直します。
人が`/VERYSILENT`で入れたときに、勝手に起動しないようにするためです。

### 同じ日の判定は、いまは届きにくい経路にあります

「同じ日に2回以上は出さない」を実装しましたが、**通常の流れでは到達しません。**
再提示の最短の間隔が24時間のため、間隔の判定が先に効くためです。

残してあるのは、保存した内容を手で編集されたときや、回数を持たない古い状態を読んだときに効くからです。
テストはその経路を通しています。

### 取得先を絞ります

`packages[].url`は`https`の`github.com`に限ります。
マニフェストを乗っ取られても、引く先を移せないようにするためです。

同じ理由でインストーラーの引数はマニフェストに入れません。

## 3つのモード

利用者が3つから選びます。
3つを別々の仕組みにはせず、**1本の状態機械にゲートを2つ置いた形**で表します。

- 取得ゲート。更新ありからダウンロードへ進むところ
- 適用ゲート。取得済みからインストールへ進むところ

| モード | 取得ゲート | 適用ゲート | 止まる位置 | 利用者が押す回数 |
| ---- | ---- | ---- | ---- | ---- |
| A 自動 | 自動 | 自動 | 原則止まりません | 0回 |
| B 取得だけ自動 | 自動 | 手動 | `Downloaded` | 1回 |
| C お知らせのみ | 手動 | 手動 | `UpdateAvailable`と`Downloaded` | 2回 |

「取得は手動だがインストールは自動」は意味を成しません。
そのため設定にはトグル2つではなく、ラジオボタン3つを置きます。

**更新があるかの確認は、どのモードでも自動で行います。**
モードCで止まるのはダウンロードとインストールだけです。

## 既定値

**モードB（取得だけ自動）を既定にします。**

理由は3つです。

1. 未署名の期間にモードAを既定にすると、最も悪い組み合わせになります。自動のはずなのに、席にいない利用者がSmartScreenの「詳細情報」から「実行」を押すまで完了しません。自動化は途中で人の介入を求めた時点で価値がなくなります
1. モードCを既定にすると更新が届きません。`.NET`をself-containedにしているため、`.NET`自体の脆弱性の修正もアプリを出し直さないと届かないためです
1. モードBは押すのが1回で、押した瞬間に待ち時間がありません。ファイルは手元にあるので、警告が出ても自分が押した文脈の中で判断できます

署名が通り、SmartScreenの警告が実機で出なくなったら、既定をモードAへ移してかまいません。
ただし条件が1つあります。

**利用者が明示的に選んだ設定は上書きしないでください。**
状態に「利用者が自分で選んだか」を持たせ、既定値の変更は一度も触っていない利用者にだけ適用します。
変更した版のリリースノートにも書きます。

## 状態遷移

| 状態 | 意味 | 次へ進む条件 |
| ---- | ---- | ---- |
| `Idle` | 最新、または未確認 | 起動の3分から10分後に1回。以降は24時間の前後2時間 |
| `Checking` | マニフェストを照会中 | 自動 |
| `UpdateAvailable` | 新しい版があり、未取得 | 取得ゲート。AとBは自動、Cはボタン |
| `DownloadHeld` | 条件により取得を保留 | 条件の解消、または「今すぐダウンロード」 |
| `Downloading` | 取得中 | 自動 |
| `DownloadPaused` | 回線断などで中断 | 条件の解消、または手動 |
| `Downloaded` | 取得完了。署名とSHA-256の検証済み | 適用ゲート。Aは自動、BとCはボタン |
| `InstallHeld` | 条件により適用を保留 | 条件の解消、または「今すぐインストール」 |
| `Installing` | 保存してから自プロセスを終了し、インストーラーを実行 | 自動 |
| `Succeeded`と`Failed` | 次回の起動時に版を照合して確定 | - |

「条件の解消」は、1分ごとに手元の状態と環境だけで見直します。
周期の確認だけに頼ると、電池で保留したものをAC電源に挿しても翌日まで動きません。
失敗のあとの1分、5分、15分の待ちも、使われないまま切れます。

見つけた更新はメモリにしか持ちません。
そのため途中の状態のまま起動したときは、起動の待ちが明けた時点で確認します。
確かな答えを得るまで、5分、15分、1時間と空けて試し直します。
待ちは壁時計と単調時刻の両方で測り、どちらかが越えたら終えます。
壁時計だけだと、時計が戻った幅だけ試し直しが止まります。

使い切りの1回にすると、起動した直後に回線がまだつながっていないだけで、途中の更新が翌日まで止まります。
待たずに試すと、回線が切れているあいだ毎分叩き続けます。
通信の失敗と、署名の通らない応答は答えに数えません。
公衆Wi-Fiの認証ページも後者に入ります。

### モードAでも適用を止める条件

止めたときはモードB相当へ降格し、通知を出します。

1. 計測が動作中、または未保存の計測データがある
1. 計測の終了から5分以内
1. `SHQueryUserNotificationState()`が`QUNS_ACCEPTS_NOTIFICATIONS`以外を返す。全画面、プレゼンテーション、ロック、応答不要の時間帯などです
1. アプリの起動から10分未満

「自動なのに勝手に再起動された」よりも「自動のはずが1回だけボタンを求められた」ほうが、被害が小さいという判断です。

**設定画面にこの例外を明記してください。**
書かないと「自動にしたのに更新されない」という不満になります。

なお計測の機能は、現時点のクライアントの範囲に入っていません。
将来入れる場合は、**計測の状態を再起動をまたいで復元できるように作ってください。**
復元できるなら、この保留の条件は要らなくなります。

### 保留の理由は必ず見せる

保留したときは理由を文字で示し、「今すぐ実行」の脱出口を必ず置きます。
「なぜ更新されないのか分からない」は、更新の仕組みに対する最大の不満の源です。

## 更新マニフェスト

### 置き場所

このリポジトリのGitHub Releaseのアセットとして`update.json`を出します。
確認先は次のURLです。

```text
https://github.com/223n/FursuitWeather_Windows/releases/latest/download/update.json
```

決め手は3つです。

1. 既存の`publish`ジョブが持つ`contents: write`だけで完結し、**ほかのリポジトリへ書き込む資格情報がゼロになります。**本体のFursuitWeatherは`main`へのpushで本番へ自動デプロイするため、そこへの書き込み権限は「本番サイトへ任意のコードを流す力」と同じです
1. GitHubの`latest`は「最新の非プレリリースかつ非ドラフト」と定義されるため、プレリリースの制御を自分で書かずに済みます
1. ロールバックが`gh release edit`の1コマンドで済みます

本体のドメインのURLが必要になったら、書き込みではなく`public/_redirects`に1行のリダイレクトを置いてください。

**一度公開したURLは、利用者の手元のアプリに焼き込まれて事実上変えられません。**
パスを決め切ってから公開してください。

### スキーマ

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-09T04:00:00Z",
  "keyId": "fw-2026-01",
  "channels": {
    "stable": {
      "version": "1.4.0",
      "releasedAt": "2026-09-09",
      "notesUrl": "https://github.com/223n/FursuitWeather_Windows/releases/tag/v1.4.0",
      "severity": "normal",
      "mandatoryBelow": null,
      "unsupportedBelow": null,
      "requirements": { "minimumOsBuild": 22621 },
      "packages": [
        {
          "arch": "x64",
          "url": "https://github.com/223n/FursuitWeather_Windows/releases/download/v1.4.0/FursuitWeather-1.4.0-x64-setup.exe",
          "size": 199229440,
          "sha256": "3a7bd3e2360a3d29eea436fcfb7e44c735d117c42d1c1835420b6b9942dd4f1b"
        }
      ]
    }
  }
}
```

| 項目 | 意図 |
| ---- | ---- |
| `schemaVersion` | 知らない値なら解釈をやめ、リリースページへのリンクだけ出します。将来スキーマを作り直せる唯一の担保です |
| `generatedAt` | 前回の成功時より古ければ無視します。巻き戻しの検知です |
| `keyId` | 鍵の入れ替えの余地です。**最初から入れないと後から足せません** |
| `severity` | `security`のときに文言と再提示の間隔だけ変えます。モードの選択は上書きしません |
| `mandatoryBelow` | 真偽値の`mandatory`ではなくこちらにします。「この版より古い場合だけ必須」を1つの項目で表せ、矛盾が生じません |
| `unsupportedBelow` | 緊急の停止に使います。更新を強制するのではなく「この版は使えません」と機能を止めます |
| `requirements.minimumOsBuild` | 22621がWindows 11 22H2です |
| `packages[].url` | 版を含む恒久のURLにします。GitHub Releasesの署名付きURLは約1時間で失効するため焼き込めません |

**インストーラーの引数はマニフェストに入れません。**
マニフェストを乗っ取られたときに「任意のexeを任意の引数で実行させる」経路になるためです。
引数はクライアントに直接書き、`packages[].url`のホストも`github.com`に限ります。

プレリリースは同じ`update.json`をrcのReleaseにも添付し、検証する人には版を直接指すビルドを渡します。
`latest`は仕様上rcを指さないため、安定版の利用者へ流れることは構造的に起きません。

## 完全性の検証

### 未署名の段階

信頼の起点は、TLSやAuthenticodeではなく**自前のリリース署名鍵**に置きます。
マニフェストにSHA-256を載せるだけでは、マニフェストごと差し替えられたときに無力だからです。

- 曲線はECDSA P-256にします。Ed25519は`.NET`のBCLに未実装で、信頼の起点をサードパーティ製のライブラリに置くのは筋が悪いためです
- `update.json`をデタッチ署名し、`update.json.sig`を並べます
- 公開鍵はアプリのバイナリに埋め込みます
- 私有鍵はGitHub ActionsのEnvironment secretに置き、required reviewersを付けます

**検証の順序を固定します。**

1. 署名の検証
1. `generatedAt`が前回より新しいか
1. いまの版より新しいか。巻き戻しの防止です
1. `minimumOsBuild`
1. ダウンロード
1. `size`と`sha256`の照合
1. 実行

**署名を通す前に、JSONの中身で分岐しないでください。**

SHA-256は破損や部分的なダウンロードの早期の棄却と、利用者が手で照合するためのものです。
真正性は署名が担い、SHA-256は完全性しか担いません。

**TLS証明書のピン留めはしません。**
配信先の証明書は予告なく替わり、ピンが外れると全利用者の更新が恒久的に止まります。

### ダウンロード先の保護

同じ利用者の権限で動く別プロセスによる差し替えは、Windowsのセキュリティ境界の外側です。
目標は解決ではなく、隙を狭めることです。

1. `%LOCALAPPDATA%\FursuitWeather\update\`の下に、毎回新しいGUIDのディレクトリを作ります。固定のパスを使いません
1. `FileMode.CreateNew`で作り、既存があれば失敗させます
1. **検証から実行までハンドルを開いたままにします。**`FileShare.Read`だけを許し、ハッシュもそのハンドル越しに取り、パスで開き直さずに起動します
1. `%TEMP%`は使いません。ストレージセンサーに消される可能性があります
1. 置いてあるものを使い回すときは、署名を通したばかりのマニフェストのSHA-256と照らします。照らすのは掴んだハンドル越しです。置いてあったこと自体は信用しません

**Mark of the Webは未署名の期間は付けません。**
付ければ必ず警告が出て、「更新のたびに出る不可解なダイアログ」を無視する習慣を作るだけです。
初回のインストールはブラウザー経由で警告が出るため、READMEに「未署名です。この警告が出ます。SHA-256はこれです」と書くほうが誠実です。

### 署名が通ったあと

- `[Setup] SignTool`と`SignedUninstaller=yes`を使い、インストーラー・アンインストーラー・本体の3つに署名します
- アプリ側に`WinVerifyTrust`の検証を追加します。自前の署名は主の判定として残します
- **署名者の識別は二次的な確認に留め、拒否の根拠にしません。**SignPath Foundationの証明書は名前がほかのOSSと共通で、サムプリントも1年から3年で必ず変わります。証明書の更新で更新の仕組みが自爆する事故のほうが、この経路で防げる攻撃より起こりやすいためです
- 拡張検証（EV）の証明書は買いません。SmartScreenの即時の通過は2024年に廃止され、Microsoft自身が正当化できないと明記しています

## インストールの実行

`restartreplace`は管理者権限がないと効かない、と公式に明記されています。
`PrivilegesRequired=lowest`とは両立しないため、**自分が終了する以外に実行中のexeを置き換える方法はありません。**

### 段取り

1. 検証済みのインストーラーを用意します
1. 計測などのデータを書き出して確定します。**書き出しに失敗したらインストールを中止します**
1. 状態ファイルに`phase`と`targetVersion`と`expectedSha256`を書きます。**インストーラーの起動より前**です。逆の順序だと中断を検知できません
1. トレイのアイコンと小窓を破棄し、`AppNotificationManager.Default.Unregister()`を呼びます
1. インストーラーを起動し、自分のPIDを`/WAITPID=`で渡します
1. すぐに自プロセスを終了します
1. インストーラーは`InitializeSetup`でPIDの終了を待ちます。`AppMutex`の判定より前に走ります
1. ランタイムを入れ終えたあと、`CurStepChanged(ssPostInstall)`でアプリを起動し直します。途中で止まったときは`DeinitializeSetup`が起動し直します。呼び元がまだ動いていれば見送ります
1. 起動したアプリが`phase`を見て、実際の版と`targetVersion`を照合し、成否を確定します

### 使う引数

```text
/SP- /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /RESTARTEXITCODE=3010
/NOCANCEL /LOG="<パス>" /DIR="<現在の実行ディレクトリ>" /WAITPID=<PID> /RELAUNCH=1
```

| 引数 | 理由 |
| ---- | ---- |
| `/SP-` | **これを落とすと無人の更新が止まります。**`/SILENT`と`/VERYSILENT`は起動時の「続行しますか」を抑止せず、`/SUPPRESSMSGBOXES`でも抑止されません |
| `/NORESTART` | **必須です。**`/VERYSILENT`は再起動が必要なとき、確認なしで再起動します |
| `/RESTARTEXITCODE=3010` | 既定では「成功して再起動が要る」も0が返り、区別できません |
| `/SUPPRESSMSGBOXES` | `/SILENT`か`/VERYSILENT`との併用でのみ有効です |

`postinstall`は完了ページのチェックボックスなので、サイレント実行では意味を持ちません。

**起動し直しを`[Run]`に置かないでください。**
`postinstall`でない`[Run]`の行は、`CurStepChanged(ssPostInstall)`より前に走ります。
Innoのソース（`Setup.MainForm.pas`の`TMainForm.Install`）で確かめました。
そこで起動すると、Windows App SDKのランタイムを入れる前に本体が立ち上がります。
ランタイムの版を上げた更新では、本体がブートストラップに失敗して黙って終わります。
そのため`ssPostInstall`で、ランタイムを入れたあとに`Exec`で起動します。

ランタイムの導入に失敗したときの`MsgBox`は、起動し直したあとに出します。
`[Code]`の`MsgBox`は`/SUPPRESSMSGBOXES`でも抑止されず、誰かがOKを押すまで戻りません。
先に出すと、席にいない利用者の端末では常駐が戻らないままになります。
入っているランタイムで動ける場合もあるため、失敗しても起動は試します。

`/RELAUNCH=1`で起動し直すのは、サイレントのときだけです。
ウィザードを出しているときは、完了ページのチェックボックスに任せます。
両方で起動すると二重になるためです。

**インストールが途中で止まると、`ssPostInstall`と`ssDone`のどちらにも来ません。**
ファイルが掴まれていたり空き容量が足りなかったりすると、`/SUPPRESSMSGBOXES`がAbortを選び、黙って中止します。
`PerformInstall`が失敗すると、Innoは`TerminateApp`で抜けます。
呼び元はもう終わっているため、起動し直す者がいなくなります。
その間は暑さの通知も出ず、更新の確認も走りません。

中止しても呼ばれるのは`DeinitializeSetup`だけで、ここが受け皿です。
起動し直したかを覚えておき、済んでいなければ起動します。

呼び元のプロセスのハンドルは、`DeinitializeSetup`まで閉じずに持ちます。
閉じるとPIDが別のプロセスへ使い回され、終わったかを取り違えるためです。

**版を読む`FursuitWeather.Widget.dll`は最後に置きます。**
`[Files]`は名前順に置かれ、何もしないと305個のうち18番目に来ます。
中止したときの巻き戻しは前からあったファイルを戻さないため、版を持つファイルだけが先に新しくなりえます。
すると次の起動で版を照らしたとき、途中で終わったものを「入った」と誤って判定します。
`Excludes`で3行に分け、版が切り替わるのをほかのすべてが揃ったあとにしています。

**ランタイムのインストーラーは`[Files]`の先頭に置きます。**
111MBあり、正味でいちばん容量を使う書き込みです。
あとに回すと、空きの少ない端末では`Widget.dll`まで置き終えてから容量が尽きます。
すると中止したのに版だけが新しくなり、同じ誤判定が起きます。

### C#側の注意

`WorkingDirectory`にインストール先を指定しないでください。
インストール先にハンドルが張られます。

`AppMutex`の判定は存在ではなく`OpenMutex`の成功で行われます。
C#で`new Mutex()`する場合、**staticなフィールドで保持しないとGCでハンドルが閉じ、検出が空振りします。**

アプリは`Local\FursuitWeather.Widget`のミューテックスで1つに絞っています。
更新のために終わる途中で通知を押されると、2つ目が起動しうるためです。
2つ動くと、トレイのアイコンも暑さの通知も二重になります。

作れたかどうか（`createdNew`）では見分けません。
2つ目がハンドルを持ったまま1つ目が終わると、持ち主のいないミューテックスが残ります。
すると3つ目が「作れなかった」と見て、誰も動かない状態になります。
実際に持てるかを`WaitOne(0)`で確かめ、`AbandonedMutexException`は引き継ぎとして扱います。

## 失敗したとき

### 成否の判定は終了コードではありません

このやり方ではアプリが先に終了するため、インストーラーの終了コードを読む主体がいません。

**主の経路は次回の起動時の版の照合です。**
`phase`が`Installing`のまま残っていたら、実際の版と`targetVersion`を比べます。
一致すれば成功、しなければ中断されたインストールとして扱います。
この1つの仕組みで、電源断とスリープと強制終了が同じ経路に集まります。

### 終了コードを読む場合の罠

- `/SUPPRESSMSGBOXES`の既定の応答はAbortです。そのため**サイレント実行では実際のエラーの多くが4ではなく5になります。**5を利用者によるキャンセルだとみなすと誤診します
- 終了コードは0から8の9種類だけではありません。公式が「将来の版は追加の終了コードを返しうる」と明記しています。**分岐には必ず既定の枝を置いてください**

### 再試行の抑制

カウンターは版ごとに持ち、`expectedSha256`も鍵に含めます。
同じ版が作り直されたときに、古い抑制を引きずらないためです。

| 対象 | 上限 |
| ---- | ---- |
| ダウンロードの失敗 | 1分、5分、15分、1時間、6時間で頭打ち。24時間で自動5回まで。最後の失敗から24時間で数え直し、取得に成功したら0へ戻します |
| インストールの失敗 | 1つの版につき3回。間隔は6時間以上。同じセッションで2回試しません |
| 全体の遮断 | 異なる3つの版で連続して失敗したら、自動の更新そのものを無効にし、手動での入れ直しを案内します。入れ直して成功したら解きます。Releasesから手で入れて失敗した版を追い越した場合も解きます |

**抑制は自動の側だけに効かせ、手動のボタンは常に生かします。**

署名を通ったマニフェストが、見つけてあった更新を否定したら進めるのをやめます。
リリースを取り下げると、古いマニフェストが返って`Stale`になります。
前の答えを信じて取りに行くと、取り下げた版を入れてしまいます。
一方で、署名の通らない応答や通信の失敗では、前の状態を変えません。
誰が作ったか分からない応答で、検証済みのものを捨てないためです。

新しい版を見つけたら、ゲートを見る前に記録を張り直します。
張り直さずに見ると、前の版で積もった失敗が次の版まで止めます。
累計で数えていたころは、1日1回の確認で5回失敗すると、以後どの版も自動では取らなくなっていました。

中断を見つけた場合、**モードAでも自動では再実行せず**、確認を挟みます。
無人で壊れた状態に上書きを繰り返すのが、最も危ないためです。

### Innoのロールバックは安全網になりません

ロールバック自体は走ります。
しかしソースを読む限り、**インストールの前から存在したファイルは削除されません。**
古いファイルを退避する実装もありません。

つまり上書きの更新が途中で失敗すると、新しく置いたファイルは消える一方、上書きされたexeやDLLは新しい版のまま残る混在の状態になりえます。
「Innoに任せれば安全」という前提を置かないでください。

中止したときに起動し直すのは、この混在を承知のうえです。
起動できない場合は残りますが、黙って消えるよりは被害が小さくなります。
起動できれば、狙った版と照らして「途中で終わった」と利用者に知らせます。

### 起動しなくなった場合

4つの層で備えます。

1. ひとつ前の版のインストーラーを1本だけ残し、設定画面の奥に「ひとつ前の版に戻す」を置きます
1. 新しい版の初回の起動から30秒後に「起動できた」印を書きます。書かれないまま終わったら、次回の起動時に選択肢を出します
1. READMEとリリースのページに、手で入れ直す手順を書きます
1. `unins000.exe`は常に残るため、「設定」の「アプリ」からのアンインストールを案内の起点にします

**自動での版の巻き戻しは実装しません。**
更新、失敗、巻き戻し、更新という輪を作るためです。
利用者が少ない初版では、3と4だけに留める判断も合理的です。

### ログ

- アプリ側は`%LOCALAPPDATA%\FursuitWeather\logs\`に置きます。日ごとに分け、14日または合計20MBの早いほうで消します
- インストーラーの`/LOG`は引数なしで使いません。`%TEMP%`に作られ、消される可能性があり、場所を案内しにくいためです
- **ただし`/LOG="ファイル名"`は、ファイルを作れないとインストーラーがエラーで中止すると公式に明記されています。**起動の前に書き込みを試し、失敗したら`/LOG`を外して起動してください
- ログにはパスに利用者の名前が含まれます。外部への自動の送信はしません
- **ログの形式は予告なく変わると公式に断り書きがあります。ログを読んで成否を判定しないでください**

## 自動のダウンロードを控える条件

判定に使うAPIは、公式のドキュメントで実在を確認したものだけです。

### 従量制課金の接続

`NetworkInformation.GetInternetConnectionProfile()`と`ConnectionProfile.GetConnectionCost()`を使います。
前者は`null`を返しうるため、不明なときは安全側に倒して控えます。

控えるのは次のいずれかに当てはまるときです。

- ローミング中です
- データの上限を超えています
- 背景の通信が制限されています
- `NetworkCostType`が`Variable`です
- `NetworkCostType`が`Fixed`で、上限に近づいています
- `NetworkCostType`が`Fixed`で、取得するファイルが50MBを超えます

公式の実装ノートが「大きな転送の直前にコストを再評価せよ」としています。
**保留を解除する判定のときではなく、実際に通信を投げる直前に評価してください。**

### 電源

Windows App SDKの`Microsoft.Windows.System.Power.PowerManager`を使います。
すでに依存しているため、追加の費用がありません。

主の判定は電源の種類です。
補助として残量が30%未満かどうかも見ます。

**省電力の状態だけに依存しないでください。**
Windows 11 24H2以降で省電力のモデルが変わり、このAPIが新しいモデルを反映していない可能性が指摘されています。

### 利用者が明示的に押した取得

これらの判定を無視して実行します。
ただしボタンの近くに「従量制課金の接続です」と大きさを添えて示し、了解のうえで押させます。

設定画面ができるまでは、トレイの「更新を確認」がこの入口です。
確認のあとで取得が保留になっていれば、大きさと保留の理由を示してから「今すぐ取得しますか」と尋ねます。
押されたのは確認であり、取得への同意ではないためです。

## 時刻の測り方

**`Environment.TickCount64`は、Windowsでは`.NET 10`以前はスリープ中の時間を含み、`.NET 11`で含まなくなる**とMicrosoft Learnに明記されています。

24時間の周期をこれだけで組むと、`.NET 11`へ上げた瞬間に「よく眠るノートPCでは何日も確認が走らない」に変わります。

**壁時計（UTC）の最終確認時刻と単調時刻の両方を見て、どちらかが閾値を超えたら動かしてください。**
壁時計だけだと利用者の時刻の変更で暴発し、単調時刻だけだと再起動でリセットされます。

これは予報のポーリングにも同じ影響が及びます。
[構成](architecture.md)のポーリングの節を見てください。

## 再提示の間隔

- 起動時は、立ち上がって3分から10分後に無作為で1回
- 定期は24時間の前後2時間。端末ごとに位相をずらします
- 「あとで」を選んだあとは24時間、72時間、7日と延ばし、**7日で頭打ちにします。**1つの狙い（版とSHA-256）につき5回でトーストを止め、トレイと小窓と設定画面にだけ残します
- 提示は9時から21時のあいだ。同じ日に2回以上は出しません

回数は、新しい版を見つけたときに戻します。
戻さないと、アプリの生涯で5回しか知らせなくなります。
最後に知らせた時刻は残します。
版が変わっても、同じ日に2回は割り込みません。

割り込まなかった知らせは捨てません。
トレイのツールチップに1行残し、出せる時間帯に入ったら出し直します。

限りなく延ばす指数のバックオフは、更新を永久に届かなくします。

## 設定画面の文言

モードA、B、Cという記号は見せません。
何が起きるかで書きます。

```text
更新の扱い

○ 自動で更新する
  確認・取得・インストールまで自動で行います。インストール時は数秒アプリが再起動します。
  計測中や全画面表示中は自動で先送りし、そのときだけお知らせします。

● 取得だけ自動で行う（推奨）
  新しい版を裏で受け取っておき、インストールする時期はあなたが決めます。

○ 何もしない（お知らせのみ）
  新しい版が出たことだけをお知らせします。
  取得もインストールも、それぞれボタンを押したときだけ行います。

[x] 従量制課金の接続では自動で取得しない
[x] バッテリー動作中は自動で取得しない
[x] 計測中はインストールしない

    最後に確認した日時: 2026-09-09 14:20        [今すぐ確認]
```

**「最後に確認した日時」の常時表示は必須です。**
静かに失敗する設計では、これが「壊れていない」ことの唯一の証拠になります。
