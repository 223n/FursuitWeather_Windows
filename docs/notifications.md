# 通知の設計

どういうときにトースト通知を出すかを決めます。
配布や更新の通知ではなく、着ぐるみの判定についての通知です。

## 本体に前例が3つあります

**訂正**: この設計を始めた時点で、`docs/open-questions.md`には「本体のWeb版に前例がないため、ゼロから決めます」と書いていました。
これは誤りでした。
本体には前例が3つあり、しかも比較する値・単位・方向がそれぞれ違います。

| 前例 | 位置 | 比較する値 | 単位 | 方向 | 再通知の抑制 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| 差分バナー | `public/app.js:1510` | 日別の`outdoorWorst.grade` | 日別（日中9時から18時） | 悪化と改善を区別 | 変更内容の署名を保存。最小経過3時間 |
| 見守りモード | `public/app.js:1881` | 現在の時間帯の`outdoor.level` | 時間別 | 方向を問わない | 無し |
| 着用タイマー | `public/app.js:3400` | `outdoor.activityMinutes` | 時間別 | 悪化のみ | フラグと、悪化時の再武装 |

`src/`側（WorkersのAPI）には変化を検知するコードがありません。
悪化の判定はすべてクライアント側にあります。

**継ぐのは着用タイマーの判定基準と、差分バナーの抑制の方式です。**
見守りモードの「方向を問わない」は継ぎません。

## 判定の基準はactivityMinutesにします

`grade`を主のキーにしません。
理由が3つあります。

1. **低温側に`grade 3`が存在しません。**`optimal`が0、`coldCaution`が1、`coldWarning`が2、`coldDanger`が4です。`grade`の差を「何段階の悪化」として数えると、2から4への飛びが起きます
1. **`optimal`から`coldCaution`へ変わると`grade`は上がりますが、`activityMinutes`は45分のまま**です。行動が何も変わらないのに鳴るアラームになります
1. **`grade 4`は`danger`と`coldDanger`の両方**に割り当てられています。同じ値でも、対処は冷却と保温で正反対です

`activityMinutes`は「1回あたり何分着ていられるか」であり、行動と直結します。

## 本当の危険は通知過多ではなく沈黙です

設計を始めた時点では「通知が多すぎるのをどう抑えるか」を課題と考えていました。
実測はこれを否定しました。

本体のAPIから4都市の88時間分を取り、変化を数えた結果です。

| 地点 | `grade 4`の割合 | `grade`の上昇 | `activityMinutes`の短縮 |
| ---- | ---- | ---- | ---- |
| 那覇 | 100.0%（88時間すべて） | 0回 | 0回 |
| 大阪 | 92.0% | 1回 | 1回 |
| 東京 | 39.8% | 2回 | 2回 |
| 札幌 | 20.5% | 10回 | 10回 |

**那覇は88時間（およそ3.7日）まったく変化しません。**
着衣補正の+11℃があるため、日本の夏は判定が最上段に貼り付きます。

素朴な変化の検知だけを作ると、**最も危険な期間に何日も無音**になります。
そのため3つの層に分けます。

| 層 | 役割 | ヒステリシス |
| ---- | ---- | ---- |
| 小窓 | いまの段階と連続活動時間を常に表示する | **かけない** |
| 朝のブリーフィング | 1日1回。飽和して変化しない期間の沈黙を埋める | 該当しません |
| トースト | 行動が変わる差分だけ | かける |

**表示に遅延をかけてはいけません。**
ヒステリシスは通知にだけかけます。

## 通知の種類

| 種別 | 条件 | 重さ | 抑制 |
| ---- | ---- | ---- | ---- |
| T1 着用中止級 | `activityMinutes`が0になった | Urgent | 1日1回 |
| T2 短縮 | `activityMinutes`が前回より減った | 通常 | 同種は2時間あける。1日6件まで |
| T3 公式発表 | 環境省の熱中症警戒アラートが出た | Urgent | 抑制の対象外 |
| R1 復帰 | 0分から回復した | 通常 | 1日1回 |
| C1 打ち切りの告知 | 上限で通知を捨てた | 通常 | 1日1回。上限には数えない |

急な暑さ（`suddenHeat`）と冷房必須（`coolingRequired`）は、単独のトーストにせず朝のブリーフィングへ入れます。

### 着用中止級が出せないときは短縮へ落とす

着用中止級（T1）と短縮（T2）は同じ悪化を指すため、出すのは片方だけです。
**ただし片方を`else if`で消してはいけません。**

T1は1日1回に絞っています。
その日2回目の「活動できる状態から0分への転落」でT1が予算切れになったとき、T2へ落ちる道が無いと完全に無音になります。
2回目のT1が立つには、間に「0分から活動できる状態へ戻る」を経ています。
利用者の認識は「着られる」に戻っているため、2回目の転落は新しい情報です。

両方を候補として積み、抑制を通った先頭の1件だけを出します。

### 監視する対象

いまの時刻ではなく、**これからの数時間のうち最も厳しい時間**を見ます。

常駐アプリを使う人は、定義上PCの前にいます。
つまりまだ着ていません。
「いま悪化した」よりも「これから出るときに悪化している」ほうが行動につながります。

先読みの幅は既定3時間とし、設定で1時間から6時間まで変えられるようにします。

### 前提のガード

本体の`syncWatchBaseline`（`public/app.js:1859`）の考え方を移します。

- 前回の状態が6時間より古い、または地点が変わったときは、基準を今回の値へ合わせて**悪化と回復は通知しません**
- レスポンスの`generatedAt`が前回以下のときは、基準を更新しません。古い応答で改善を誤検知しないためです

**このガードは公式発表（T3）には掛けません。**
T3は前回の値との差分ではなく、外部の事実そのものだからです。
基準の信頼性とは独立しています。

掛けてしまうと、夜間にアプリを止める運用で毎朝の初回のポーリングがこのガードを通り、**午前5時の発表がそこで消えます。**
公式発表の状態（出ているか、解除されたか）も、ガードに関わらず常に取り込みます。
解除を取り込まないと、次の発表で立ち上がりを検出できなくなります。

### T3は「出ているか」だけで見てはいけません

**発表の識別に対象日と特別警戒の別を使います。**

真偽値1つで立ち上がりを見ると、連日の発表を1つと見なします。
本体のAPIが発表なしを返すのは0時から5時のあいだだけで、そこが唯一の立ち下がりです。
夜間にPCを止める運用ではその時間帯を一度も取得しないため、前回の真がそのまま残ります。

結果として、**熱波の2日目以降の発表がすべて無音になります。**
上の「前提のガード」でT3を外したのは、まさにこの運用を守るためでした。
ガードを外しても、立ち上がりの判定が真偽値のままでは同じ穴が残ります。

同じ理由で、警戒から特別警戒への格上げも真偽値では捉えられません。
格上げは行動が変わる情報のため、知らせます。
逆に特別警戒から警戒へ下がったときは知らせません。

本体が対象日を返さないときは、日本時間の日付で代えます。
空のまま扱うと、対象日を持たない発表が永久に「同じ発表」になります。

版を上げる前に書かれた状態には対象日がありません。
そのときは1回だけ重ねて出します。
「同じ発表」と見なして1日ぶん取りこぼすより、1回重なるほうが軽いためです。

### T1に等値の穴があります

`danger`と`coldDanger`は、どちらも`grade 4`で`activityMinutes`が0です。
数値だけを見ると、暑熱から低温へ変わったことを検出できません。

本体の差分バナーが持つ盲点でもあります。
レベルIDの変化も条件に入れて塞ぎます。

## ヒステリシス

| 方向 | 規則 | 理由 |
| ---- | ---- | ---- |
| 悪化 | **遅延もデッドバンドも設けません** | 安全側の情報を遅らせてはいけません |
| 回復 | デッドバンド0.5℃ | 境界の前後0.5℃に15.3%の時間が集まります。この幅がないと予報の改訂で帯が往復します |
| 回復 | 最小の滞留を連続2時間とします | 1時間だけの区間が10.3%あります。実測に谷が出ており、これで抑えられます |

### 回復の向きは暑熱側と低温側で逆になります

デッドバンドは「補正後のWBGTが基準から所定の幅だけ離れたか」で見ます。
**離れる向きが逆です。**

| 側 | 回復とは | 補正後WBGT |
| ---- | ---- | ---- |
| 暑熱 | 涼しくなること | 下がります |
| 低温 | 暖まること | 上がります |

「下がったか」だけを見ると、`coldDanger`から着用可へ戻ってもR1が一度も出ません。
着用中止を知らせた時点のレベルで向きを決めます。
このレベルは、R1が前回0分のときしか通らないため、必ず着用中止の時点の値です。

### デッドバンドの基準を変えました

設計の時点では「補正後のWBGTが**帯の境界**より0.5℃下へ入るまで」としていました。
実装では「**着用中止を知らせたときの補正後のWBGTより0.5℃下がったか**」に変えています。

帯の境界の値はAPIの側にあり、クライアントは持っていません。
持ち込むと判定ロジックを複製することになり、[APIの利用](api-client.md)の方針と衝突します。

境界を持たずに「わずかな改善では戻さない」という意図は満たせます。
着用中止を知らせた時点の値を覚えておき、そこから下がったかを見るためです。

**基準にする値が無いときは、直前の0分だった時点の値で代えます。**
状態を張り直したあとや初回の起動では、着用中止を知らせた記録がありません。
そこで「基準が無いから無条件で認める」としてしまうと、わずかな改善でも回復を知らせます。
回復の判定は前回が0分のときしか通らないため、直前の値は必ず「0分だった時点の値」です。

### チャタリングの抑制は実装していません

設計では「同じ境界を直近60分に3回以上往復したら、当日は悪い側へ固定する」としていました。
実装していません。

同じ種類の通知は2時間あける規則を先に設けています。
そのため**60分のあいだに同じ種類が3回出ることは、原理的に起こりません。**
規則が規則を包んでいる状態のため、足しても効きません。

同種の間隔を短くする場合は、この抑制が必要になります。
そのときに実装してください。

## 時間帯

**深夜の自前のサイレンスは実装しません。**

理由が3つあります。

1. Windows 11は「応答不可」と優先通知をすでに持ち、利用者は自分の生活時間で設定済みです。アプリが独自の夜間の規則を重ねると食い違います
1. 環境省と気象庁の熱中症警戒アラートは**当日の午前5時にも発表**されます。「23時から7時は鳴らさない」と決め打ちすると、5時の発表を握り潰します
1. **実測で深夜が安全ではありません。**那覇は88時間すべてが`grade 4`で、0時台も含みます

T1とT3だけ`AppNotificationScenario.Urgent`を使い、`IsUrgentScenarioSupported()`で保護します。
Urgentは利用者がアプリごとに一度許可する仕組みのため、濫用すると拒否されて全部止まります。
最も重い2つに限ります。

利用者が静かな時間帯を設ける設定は用意してよいですが、**T1とT3は抑制の対象外**にします。
設定画面に「静かにできるのは、行動を変えなくても命に関わらない通知だけです」と明記します。

**唯一の例外は掲示モードのあいだです。** T1とT3も含め、トーストをすべて出しません。
会場の専用の端末では掲示そのものが伝える役を担い、トーストは来場者の見る画面に重なるためです。
T1が担う先読みは、この先3時間に連続活動時間がいまより短い時間があるとき、その時刻と判定を掲示の帯に出します。
選び方はT1と同じ関数です。
判定は回して状態も進め、止めるのは文面を出すことだけです。
掲示を終えたときにまとめて出しません。
詳しくは[掲示モード](display.md)にあります。

## 1日の上限

上限は主要な設計ではなく安全弁です。
実測は1都市あたり1日0.9件で、十分に余裕があります。

- 同種の再通知は最低2時間あけます。同じ帯への再突入も同じ扱いです
- 1日の総数はT1とT3を除いて6件までとします。超えたら「今日はこれ以上お知らせしません」を1件だけ出して止めます。黙って止めるより安全です
- 同じ状態が続くときの再掲は**朝のブリーフィングが担います**。トーストで繰り返しません
- 朝のブリーフィングは既定でONにし、8時に出します。今日の最悪の判定、適した時間帯、冷房の要否、急な暑さ、公式の発表の状況を1件にまとめます

### 朝のブリーフィングの出し方

- 出す時刻は既定で8時です。設定で変えられます
- **正午を過ぎたら、その日は出しません。**昼を回ってから「今日の予定」を知らせても遅く、その時間帯の悪化はトーストの層が受け持ちます
- 夜にPCを起動したときへ持ち越しません。翌朝のぶんと紛らわしくなるためです
- 同じ日には1回だけ出します
- **判定が変わっていなくても出します。**これがこの層の目的です。変化の検知だけでは、飽和して変化しない期間に何日も無音になります
- 適した時間帯のうち、過ぎたものは落とします。遅れて出したときに、もう来ない時間を勧めないためです。ただし読めない値は落とさずに残します

## 低温側の扱い

| レベル | `activityMinutes` | 扱い |
| ---- | ---- | ---- |
| `coldDanger`（`grade 4`） | 0 | T1。ただし熱中症の導線は付けません |
| `coldWarning`（`grade 2`） | 45から30 | T2 |
| `coldCaution`（`grade 1`） | 45（変わりません） | 通知しません。小窓の表示だけ |
| `optimal`（`grade 0`） | 45 | 通知しません |

熱中症の応急対応への導線は、本体の`public/app.js:1196`と`public/display.js:343`にある条件をそのまま踏襲します。
低温の`grade 4`に熱中症の手順を出すのは誤誘導です。

## 文面とボタン

タイトルは最大2行、追加の2要素と合わせて最大4行です。
ボタンは最大5個まで置けますが、3個までに抑えます。

```text
T1（暑熱）
  タイトル  着用中止（東京都千代田区）
  本文1     15時ごろ 危険 ・ 連続10分 → 0分
  本文2     屋外での着用を中止し、冷房環境へ退避してください
  ボタン    もしものとき / 時間別を見る

T1（低温）
  タイトル  着用中止（札幌市）
  本文1     6時ごろ 低温危険 ・ 連続30分 → 0分
  本文2     凍傷とスーツ素材の低温劣化の恐れがあります
  ボタン    時間別を見る

T2
  タイトル  連続20分 → 10分（東京都千代田区）
  本文1     14時ごろ 警戒 → 厳重警戒
  本文2     10分以内にとどめ、屋内の冷房環境へ退避してください
  ボタン    時間別を見る / 2時間おやすみ

T3
  タイトル  熱中症警戒アラート（東京都）
  本文1     環境省・気象庁が発表しました
  本文2     着ぐるみの判定は既に「危険」です。屋外の予定を主催と確認してください
  ボタン    環境省の発表を見る / 時間別を見る

R1
  タイトル  着用を再開できる可能性があります（東京都千代田区）
  本文1     17時ごろ 厳重警戒 ・ 連続10分
  本文2     体調と装備を確認してください
  ボタン    時間別を見る
```

- 「もしものとき」はT1かつ暑熱側のときだけ置きます
- 「時間別を見る」は小窓を前面に出します
- 「2時間おやすみ」はその種別だけのスヌーズです。**T1には置きません。**中止級を黙らせるボタンを用意すべきではありません
- 「了解」だけのボタンは置きません。シェルがすでに閉じるボタンを持っています

## 改善の通知はしません

例外は1つだけです。

改善は「行動をやめてよい」しか意味せず、行動を要するアラームになりません。
通知の総数が倍になり、悪化の通知の価値が薄まります。
そして「もう安全だ」と誤読させる危険があります。
本体の通年の注意文が述べるとおり、`grade 0`でも熱中症は起こります。

例外はR1（着用中止から着用可への復帰）だけです。
待っている人がいるときに、実際に行動が変わります。

**本体の差分バナーは改善も出していますが、方針を意図的に変えます。**
バナーは目に入るだけですが、トーストは割り込むためです。

## 実装の置き場所

`FursuitWeather.Core/Changes/`に純粋な関数として置きます。
入力は「前回の状態」「今回のレスポンス」「現在時刻」、出力は「発火すべき通知の一覧」です。

UIに依存させないため、Linuxのランナーでもテストを回せます。

## 実装の配線

判定と文面はCoreに、保存と発行はUIの層に置きます。
型ごとの役割は[構成](architecture.md)の「通知の配線」にあります。

取得は11分ごとです。
そのたびに朝のブリーフィングと変化の検知を1回ずつ回し、出すものがあれば出します。

**朝のブリーフィングを先に出します。**
シェルは後から出したものを上へ積むため、同じ回に悪化とブリーフィングが揃ったときは行動を変える側が手前に来ます。

### 設計から変えた点

| 箇所 | 設計 | 実装 | 理由 |
| ---- | ---- | ---- | ---- |
| T3の本文2 | 着ぐるみの判定は既に「危険」です | 着ぐるみの判定は「（ラベル）」です | 発表時に必ず`danger`とは限らないためです。「既に」を落として実際のラベルを入れます |
| T1の本文1 | 連続10分 → 0分 | 前回も0分なら「連続0分」 | `danger`から`coldDanger`へ移ると前後とも0分になり、「0分 → 0分」は何も伝えないためです |
| ボタン | 最大3個を置く | まだ置いていません | 本文の表示までを先に通しました。ボタンは別に足します |

### まだ足していないもの

- トーストのボタン（「もしものとき」「時間別を見る」「環境省の発表を見る」「2時間おやすみ」）
- 先読みの幅を1時間から6時間で選ぶ設定
- 朝のブリーフィングの時刻を変える設定
- 通知の履歴を設定画面から見る手段

いまはトーストの本文を押すと小窓が前に出ます。
「時間別を見る」と同じ動きのため、ボタンが無くてもその導線だけは通っています。

| チャタリングの抑制の定数 | 産業の警報設計の知見は二次情報から取りました。方向は複数の出典で一致していますが、個々の数値をそのまま写す前に一次資料に当たってください |
| 実測の代表性 | 4都市88時間は2026年9月上旬の値です。「63.1%が`grade 4`」は年間の代表値ではありません。ただし結論（飽和する期間が存在し、変化の検知だけでは沈黙する）は飽和期間の存在だけで成り立つため、季節が変わっても設計の判断は覆らないと**考えています** |
| 通知が読まれ行動につながったかの検証 | 手段がありません。本体はテレメトリを持たない方針で、Windows版も同じにします。設定画面に通知の履歴を置き、利用者自身が振り返れるようにするのが代替です |

## 決めきれていない前提

**利用者像が確定していません。**

「PCの前にいる＝まだ着ていない計画者」という前提で先読みの窓を設計しました。
会場でノートPCを開くハンドラーが主な用途なら、先読みではなく現在時刻の監視が正しくなります。

折衷案として、小窓に「今日は着る」の宣言のトグルを置き、宣言された日だけ先読みの窓を1時間へ縮めて感度を上げる方法があります。

もう1点、**判定はその地点の屋外の推定値**であり、利用者の実際の居場所とは限りません。
デスクトップの座標が自宅で、活動場所が別ということは普通に起こります。
地点の複数登録か、活動場所の別指定の検討が別に要ります。
